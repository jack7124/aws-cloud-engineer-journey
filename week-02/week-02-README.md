# Week 2 Cloud Engineer Journey: IAM policies 
### Concepts: Concepts: users/groups/roles, policy types (identity-based, resource-based, managed vs inline), least privilege, the policy evaluation logic (explicit deny always wins).
##### This week, I learned more in-depth about the interactions of IAM policies in AWS, their types, and configuring them myself. 

In this directory, I have included a json file of an S3 user test profile. The policy allows the S3 test user to Put and Get Objects to S3 based on a training bucket under my name. This is an indentity-based customer managed policy, meaning it is an IAM user policy that I created and then directly attached to the s3-test-user. A resource-based policy would be attached to the S3 bucket itself, like an S3 Bucket Policy. It is customer managed since it exists independently in IAM and can be attached to identities, not embedded to one user/role/group like an inline policy. If s3-test-user were to be deleted, the S3UploaderOnly-JacksonMiller policy would still remain and could be reattached to a different user or role later. To be more specific, this policy follows least privilege by allowing only S3:PutObject and S3:GetObject into one specific S3 bucket. I also followed a debugging lab where the s3 test user (in IAM Simulator) attempted to move a test file into the ARN AWS S3 my-training-bucket-JacksonMiller bucket, but it was implicitly denied as that file move goes to the ENTIRE bucket, not every object under that bucket--which are considered seperate resources. By adding a /* so it becomes -> "Resource": "arn:aws:s3:::my-training-bucket-jack/*", it is now an object resource move not a bucket resource move. I really enjoy IAM policies!
